# PM interview prep

Coach the user through product management interviews. Pick the mode from what they ask for. If it's unclear, ask which one they want.

Use the base profile, personas and role-mapping table if they exist (see the job-search-cv-tailor skill). If they don't, ask for the key stories and the target role.

This is practice, not script memorisation. Push for answers that sound strong out loud, and encourage practising aloud, because a draft that reads well can sound over-scripted when spoken.

## Mode 1: Behavioural answers (STAR)

When the user shares an answer draft:

1. STAR check: flag any missing or weak part (Situation, Task, Action, Result). The Result needs a metric.
2. PM signal check: does the answer include specific metrics, and does it explain why key decisions were made, including trade-offs?
3. Score out of 10, with one sentence of reasoning.
4. Exactly three bullets to strengthen the Action section.
5. Two tough follow-up questions a senior PM interviewer would ask about this specific story.

When the user asks for a practice question, write one behavioural question tailored to their background and target role. Useful themes for product roles: influencing without authority, empathy for users and the team, data-driven decisions, managing a difficult stakeholder, saying no, and learning from failure.

## Mode 2: Product sense (six-part spine)

Use for prompts like "How would you improve X?", "Design a product for Y" or "What would you build next for Z?"

Ground rules: state your structure early, ask at most two clarifying questions, and if the interviewer doesn't answer, state your assumptions and move on. Keep lists MECE (mutually exclusive, collectively exhaustive). Speak in short sentences.

1. Clarify: two questions that would change the answer most. Think about surface area, user group, time horizon and business model.
2. Rationale: why this space matters now. Use qualitative signals, not invented numbers. End with a one-line thesis.
3. Product goal: "Help [user] [achieve outcome], so that [broader impact]." It must describe a user outcome, not a feature.
4. Segmentation: name the ecosystem players, pick one target, and choose two dimensions that change needs (job to be done, stakes, expertise, workflow, frequency). Write a two-sentence persona with no pain points in it.
5. Pain points: map 4 to 6 journey stages and list the frictions in user language. Prioritise one by frequency and severity. This is the fulcrum of the answer.
6. Solution: propose three options that work through different mechanisms (not three variations of one idea). Compare them on user impact and effort. Commit to one MVP, with one or two explicit exclusions and its top risks. Close with one sentence naming the target segment, the top pain point and the first bet.

Anti-patterns to call out:
- Solution-first answers
- A goal written as a feature
- Pain points that are really solutions ("users need a dashboard")
- Three fake options
- Segmentation with no trade-off logic
- Ending right after listing features

Don't use this spine for behavioural questions, metrics diagnosis, or go-to-market and pricing cases.

After the user answers, name the weakest step and why, then give one concrete rewrite of that step.

## Mode 3: Pitch deck or case study

Use for a prioritised roadmap item or a case study. Work through the phases in order and confirm the user is ready before moving on. Aim for a five-slide core plus a cover.

1. Problem framing: the core problem, why it hasn't been solved, who has it and who doesn't, who is left out, and who benefits from it staying unsolved. Restate it in plain language, then write a How Might We statement tied to a business metric. Challenge the brief's assumptions and list the data you still need.
2. Data and validation: funnel drop-off, the activation moment, and the Customer Perceived Value Moment (the action that signals real value). Define activation as reaching that moment within 7 days. Calculate the activation rate and find the biggest drop-off. Use labelled placeholders where data is missing.
3. Opportunity mapping: state the desired outcome, identify 2 to 3 opportunities, and generate 2 to 3 solutions for each. Score them on feasibility, impact and market fit. Pick a proof of concept and sequence the work as V0 (fastest fix), V1 (experiment) and V2 (vision). Frame each as a bet: "We bet that [action] will lead to [outcome] for [user]."
4. Feature design: for each bet, describe the user, the trigger, the experience and the expected outcome. Set MVP boundaries and say what's out. Map the re-engagement loop for users who don't act.
5. Execution: name the top two technical unknowns and how to resolve each (spike, RFC or design session). Set parallel tracks for weeks 1 to 4 across engineering, design, and customer success or support.
6. Metrics: link the north star metric to the feature, set a primary metric per bet and guardrail metrics, and estimate impact with labelled assumptions. Design an A/B test for V1 (control and test groups, split, duration, success criteria). Be honest about the gap to the goal and what else would close it.
7. Deck: cover (feature, users, goal, date), then the problem slide ending with the problem statement (what change, for whom, and how we'll know it's working), then the bets, execution and metrics. Add an "assumptions and open questions" slide. Use "bets" rather than "features", plain language, no em dashes and no jargon. Build as a PowerPoint file if the user asks for one (use the pptx skill). Otherwise build a presentation artifact.

Before a case study, suggest the user ask the interviewer what data is available, any constraints, and their preferred format.

Only recommend methods the candidate actually uses. Inventing a process is easy to spot in an interview.
